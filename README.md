# Oimo

SaaS-система для заведений общественного питания: каждая компания работает в изолированном аккаунте со своими заведениями, кассами, сотрудниками, поставщиками, складами, меню, финансами и продажами. Внутри аккаунта поддерживаются приходные поставки, расчёты с поставщиками, складские перемещения, инвентаризация, производство и порционная продажа через POS.

## Запуск

Для рабочего режима нужен Docker Desktop. HTML-файлы нельзя просто открывать с диска: вход и документы обслуживает API, а общие данные хранятся в PostgreSQL.

```bash
cp .env.example .env
python3 scripts/init_pin_key.py
docker compose up -d --build
docker compose ps
```

После запуска откройте <http://127.0.0.1:8000/login.html>.

После чистого запуска существует только системная учётная запись владельца SaaS-платформы: `platform` / `ChangeMe-Platform-2026`. Клиентский аккаунт, первое заведение, владелец аккаунта и основная касса создаются через мастер в кабинете платформы.

Перед реальной эксплуатацией обязательно замените все стартовые пароли в `.env` **до первого запуска базы**. Пароли хешируются на сервере, а браузер получает только защищённую `HttpOnly`-сессию. При изменении пароля кассы её старые сеансы отзываются.

Веб-интерфейс работает на порту `8000`, API — на `8001`, PostgreSQL — на `5432`. Порты и пароли меняются в `.env`.

## Рабочий процесс

Админ-панель сгруппирована по модели ресторанных POS-систем: «Меню», «Склад», «Финансы», «Статистика» и «Доступ». В «Доступе» отдельно настраиваются заведения, кассы и сотрудники. Внутри «Склада» находятся остатки, поставки, перемещения, списания, инвентаризации, производство, отчёт по движению и поставщики.

1. Владелец платформы входит в отдельный кабинет `platform.html` и проходит мастер подключения: создаёт аккаунт компании, заполняет профиль бизнеса, отдельно указывает название и адрес первого заведения, задаёт тариф и доступ владельца. Вместе с первым заведением автоматически создаётся основная касса.
2. Администратор клиента входит с выданными данными и видит только свою компанию.
3. Администратор компании завершает настройку первого заведения или создаёт дополнительные заведения. Для каждого заведения настраиваются склад, кассы, график и финансовый счёт; поставщики ведутся в общем справочнике аккаунта.
4. Сотрудники создаются в общем разделе аккаунта и получают должность. Руководитель, кладовщик, производство и маркетолог входят по личному логину и паролю; кассир, официант и администратор зала работают на кассе по личному PIN. Основное заведение сотрудника используется для смен и отчётов, но не создаёт отдельный аккаунт.
5. Перед продажей сотрудник выбирает своё имя на терминале и вводит PIN. Сеанс кассира действует до окончания сеанса терминала (по умолчанию 7 дней), смены кассира или закрытия смены. При закрытии смены действующий сеанс не требует повторного PIN. Если сеанс уже истёк, кассир выбран автоматически, а введённая сумма наличных сохраняется до подтверждения PIN. При смене кассира терминал остаётся авторизованным, а открытый чек очищается после подтверждения.
6. Ответственный сотрудник открывает «Склад → Поставки», выбирает склад и поставщика, переносит в одну приходную накладную все фактически полученные продукты, количество и закупочную цену.
7. При проведении поставки остаток выбранного склада увеличивается, а себестоимость каждой позиции пересчитывается по средневзвешенному методу.
8. Оплату можно не указывать, внести частично или разбить на несколько счетов. Оплаченная сумма автоматически появляется в движении денег, неоплаченный остаток — в долге поставщику.
9. Производство выпускает блюдо по техкарте в килограммах; сервер списывает сырьё выбранного склада.
10. Готовая партия передаётся на раздачу. Только после этого блюдо доступно кассиру порциями.
11. POS создаёт чек по серверной цене, записывает в него выбранного сотрудника и связывает проданные порции с партией на раздаче. Готовые закупные товары списываются со склада заведения.
12. При закрытии раздачи количество проданных порций берётся из кассы и не редактируется вручную.

Перемещение между складами проходит через запрос получателя, согласование, отгрузку склада-отправителя и фактическую приёмку склада-получателя. На время инвентаризации движения выбранного склада блокируются.

## Данные и безопасность

Раздел «Настройки» содержит общие параметры компании, информацию о подписке, заказы, доставку, ограничения действий сотрудников и шаблон чека. Настройки сохраняются в серверном состоянии компании и применяются после обновления кассы. Обслуживание, доставка и округление рассчитываются сервером; дробные порции учитываются в продажах, возвратах и закрытии раздачи. Изменение валюты не конвертирует существующие суммы. Логотип для чека — JPEG, PNG или GIF до 5 МБ.

Онлайн-оплата подписки, фискальный регистратор, налоги и табель рабочего времени пока не подключены; интерфейс явно показывает эти ограничения. Производство и кассовые смены обязательны для текущей модели учёта. Подтверждение защищённых действий выполняется входом по личному PIN управляющего или администратора зала.

- У каждой компании есть собственный `tenant_id`; рабочее состояние, пользователи, аудит и техкарты фильтруются сервером по этому идентификатору.
- Владелец платформы управляет компаниями и подписками, но не открывает их рабочие документы через обычный API.
- Администратор компании не может видеть список клиентов платформы или данные другой компании.
- Приостановка компании завершает все её активные сеансы.
- Тариф хранит лимит заведений и применяется сервером при создании нового заведения.
- Все рабочие документы и продажи хранятся в общей серверной базе, а не в `localStorage` браузера.
- Роль и права сотрудника проверяются API для каждого действия.
- Кассир не получает закупочные документы и себестоимость, производство не может проводить продажи, а кладовщик не может выпускать блюда.
- Пароли хранятся как `PBKDF2-SHA256`-хеши с индивидуальной солью.
- PIN кассира также хранится только как солёный хеш. После пяти неверных попыток ввод блокируется на пять минут.
- Сервер ведёт неизменяемый журнал складских движений и аудит действий пользователей.
- Номер накладной необязателен; если он указан, повторная накладная того же поставщика отклоняется.
- Администратор компании управляет заведениями, кассами и сотрудниками из отдельных реестров без переключения всего интерфейса в «режим точки».
- Несколько руководителей могут работать в одном аккаунте; искусственного правила «один управляющий на одно заведение» нет.

Для HTTPS-развёртывания установите `SESSION_COOKIE_SECURE=true` и публикуйте приложение через TLS-прокси. Текущий проект содержит SaaS-основу и локальный кабинет платформы; для публичного коммерческого запуска дополнительно нужны домен, HTTPS, управляемая PostgreSQL, автоматические резервные копии, почтовая доставка приглашений, мониторинг и интеграция с выбранным платёжным провайдером.

## Ограничения

Печать в POS пока является обычной браузерной печатью, не фискальным чеком. До эксплуатации потребуются интеграция с зарегистрированной ККМ, банковским терминалом, резервное копирование и HTTPS.

Остановка без удаления данных:

```bash
docker compose down
```

Команда `docker compose down -v` удаляет базу без возможности восстановления; используйте её только для осознанного сброса тестовых данных.

PIN-коды терминала проверяются по хешу. Для просмотра администратором новые PIN также сохраняются зашифрованными; просмотр выполняется отдельным запросом с проверкой прав и записью события без самого PIN. Старые хеши нельзя восстановить: сотруднику нужно явно назначить новый PIN. Ключ `.runtime/employee-pin.env` хранится отдельно от базы; сохраняйте его при переносе сервера и резервном копировании. Скрипт инициализации не заменяет существующий ключ.
