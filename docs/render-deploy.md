# Развёртывание Oimo на Render

Конфигурация `render.yaml` создаёт один Docker Web Service и PostgreSQL 17 в Frankfurt. В ней выбраны **платные** ресурсы; до подтверждения создания проверьте стоимость в Render. Облачные ресурсы этой подготовкой не создаются.

## Первый запуск

1. Загрузите исходники в приватный GitHub/GitLab репозиторий. Не добавляйте `.env`, `.runtime`, `backups`, дампы базы или ключи. В текущей папке Git ещё не инициализирован.
2. В Render выберите **New → Blueprint**, подключите репозиторий и файл `render.yaml`.
3. Задайте `PLATFORM_INITIAL_PASSWORD`: уникальный пароль минимум 16 символов. Логин владельца платформы — `platform`. `EMPLOYEE_PIN_KEY` генерируется автоматически; сохраните его в менеджере паролей. Он нужен вместе с резервной копией базы для восстановления PIN сотрудников.
4. Проверьте тарифы и подтвердите создание ресурсов. Pre-deploy применит схему и миграции; при ошибке развёртывание остановится. Повторный deploy не заполняет базу заново.
5. Откройте `https://<имя-сервиса>.onrender.com/login.html`, войдите как владелец платформы. Панель SaaS — `/platform.html`. Создайте демонстрационную компанию и сотрудников через интерфейс. Админка компании — `/admin.html`, терминал — `/index.html`.
6. Если подключаете свой домен, добавьте его полный HTTPS-адрес в `CORS_ORIGINS` (несколько адресов через запятую). Адрес Render добавляется автоматически.

Смена `PLATFORM_INITIAL_PASSWORD` после первого запуска не меняет пароль существующего пользователя: переменная используется только при создании владельца платформы.

## Данные

Новая база не содержит ваши локальные компании, продажи, остатки и фотографии. Для презентации можно создать отдельную демонстрационную компанию. Для переноса существующих данных нужен отдельный backup/restore PostgreSQL и **тот же EMPLOYEE_PIN_KEY**, который использовался локально; установите его до запуска приложения. Не публикуйте дамп или ключ в Git. Не восстанавливайте дамп поверх работающей базы без резервной копии и согласованного окна обслуживания.

Изображения каталога и рабочие данные сохраняются в PostgreSQL. Persistent Disk веб-сервису не требуется. Доступ к БД в Blueprint разрешён только по внутренней сети Render. Храните независимую резервную копию и проверяйте восстановление.

## Проверка перед презентацией

- `/health` возвращает `status: ok`, страницы и фотографии открываются по HTTPS.
- Вход владельца, вход сотрудника по PIN, права производства/кассира работают.
- На тестовой компании: поставка → производство → передача → приём кассиром → продажа → смешанная оплата → чек и отчёт Excel.
- Проверить отказ приёмки, списание с подтверждением руководителя, закрытие смены и остатки.
- Выполнить redeploy и убедиться, что данные и PIN сохранились.
- Пройти демонстрацию с устройства и сети, которые будут использоваться на встрече.

Проверка локального Docker-образа не заменяет этот прогон на самом Render. Подготовка подходит для демонстрационного развёртывания, но не является подтверждением готовности к коммерческой эксплуатации: фискализация, интеграции с банковскими терминалами/оплатой подписок, нагрузка и восстановление требуют отдельной проверки.

Документация Render: https://render.com/docs/blueprint-spec и https://render.com/docs/free. Бесплатный веб-сервис засыпает при простое, а бесплатная PostgreSQL имеет ограниченный срок жизни; для презентации и хранения рабочих данных в Blueprint выбраны платные ресурсы.

## Локальная проверка облачного образа

`docker build -f render.Dockerfile -t oimo-render-check .`

`python3 scripts/render_smoke.py`

Проверка создаёт отдельные временные контейнеры и сеть, применяет миграции дважды, проверяет страницы, вход и cookie. В конце удаляет только созданные ею ресурсы. Нужны Docker и свободный локальный порт 18080. Рабочая база не используется.
